<objective>
Implement REL-02: configure `req` at `Paddle.Client.new!/1` with `retry: :transient, max_retries: 3` so the SDK automatically retries on Paddle's transient failure modes (429 + 5xx) and on transient transport errors (timeout/econnrefused/closed). Purpose: Real-world Paddle production conditions involve transient infrastructure failures and rate-limiting. Without a built-in retry policy, every consumer (Accrue, future SDK users) re-implements the same exponential-backoff-honoring-Retry-After loop. Per D-17, the policy lives in `Client.new!/1`; per D-18, the locked per-call override is `:retry` (boolean) — `false` disables that call's retry, omitted/`true` inherits client policy. Per D-19/D-20, the public surface exposes ONLY `:retry` (boolean); `:max_retries`, `:retry_delay`, `:retry_log_level`, `:timeout`, etc. are explicitly REJECTED for v1.2 vocabulary.

Output: Two-line addition to `Paddle.Client.new!/1` (`retry: :transient, max_retries: 3` inside the `Req.new` block); five Agent-backed adapter tests in `test/paddle/http_test.exs` covering the full D-17 + D-18 contract; CHANGELOG `### Added` bullet documenting the retry policy and per-call override.

This plan does NOT add a `:max_retries`, `:retry_delay`, or `:retry_log_level` opt to public functions (D-20). It does NOT add custom retry-decision logic — `retry: :transient` is verified in 08-RESEARCH.md to satisfy D-17 exactly for Paddle's API surface. It does NOT change `Http.request/4` (the per-call `:retry` opt flows through automatically because Req already accepts `:retry` as a known option; the Plan 03 `Keyword.pop(opts, :idempotency_key)` does NOT pop `:retry` so it survives into the final opts list and reaches Req).

```elixir
defmodule Paddle.Client do
  @enforce_keys [:api_key, :environment]
  defstruct [:api_key, :environment, :req]

  def new!(opts \\ []) do
    api_key = Keyword.fetch!(opts, :api_key)
    environment = Keyword.get(opts, :environment, :sandbox)

    base_url =
      if environment == :live,
        do: "https://api.paddle.com",
        else: "https://sandbox-api.paddle.com"

    req =
      Req.new(
        base_url: base_url,
        auth: {:bearer, api_key},
        headers: [{"Paddle-Version", "1"}]
      )
      |> Paddle.Http.Telemetry.attach()

    %__MODULE__{api_key: api_key, environment: environment, req: req}
  end
end
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Paddle API ↔ retry budget | A misbehaving Paddle endpoint returning persistent 5xx could be retried up to 3 times per call; the `max_retries: 3` cap (D-17) bounds the amplification. |
| Caller ↔ per-call `:retry` override | Caller-supplied boolean `retry: false` disables retry for a single call; `true` or omitted inherits client policy. No other values accepted (passing `retry: 7` would pass through to Req, which would treat it as a non-falsy `:atom` and behave per Req's contract — but the locked v1.2 vocabulary documents only `false` as the override, and consumer documentation should reflect this). |
| Retry-After header ↔ retry timing | Paddle controls retry backoff via `Retry-After` on 429/503; the SDK honors this automatically through Req's built-in `get_retry_after` logic (verified from Req source in 08-RESEARCH.md). The SDK does NOT impose a tighter delay than Paddle requests. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-08-12 | D (Denial of Service — retry amplification against Paddle) | Automatic retry on 429/5xx | mitigate | `max_retries: 3` (D-17) hard-codes the ceiling — total 4 requests per public call.
