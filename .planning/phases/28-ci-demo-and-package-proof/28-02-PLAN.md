<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub runner to CI workflow | Pull requests and pushes execute the release-readiness proof in `.github/workflows/ci.yml`. |
| Demo test process to PostgreSQL service | Demo tests connect to an ephemeral GitHub Actions PostgreSQL service. |
| Hex artifact to fresh Mix consumer | The smoke helper builds/unpacks the package and compiles a downstream app against the artifact. |
| Optional deps to core SDK consumer | The package smoke proves the core SDK compiles without downstream `plug` or `bandit`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28-04 | Tampering | `.github/workflows/ci.yml` action dependencies | mitigate | Preserve pinned GitHub Action SHAs from existing workflow patterns rather than switching to floating tags. |
| T-28-05 | Information Disclosure | CI jobs | mitigate | Do not add live Paddle sandbox/provider-state CI or secrets; all proof remains deterministic per D-18. |
| T-28-06 | Denial of Service | `demo-postgres` job | mitigate | Use GitHub Actions PostgreSQL service health checks and `DB_HOST=localhost` before running `cd demo && mix test`. |
| T-28-07 | Tampering | `bin/package_smoke.sh` package proof | mitigate | Use `mix hex.build --unpack` to exercise real package files instead of custom file-copy simulation. |
| T-28-08 | Repudiation | CI failure attribution | mitigate | Use separate named jobs and explicit step names so maintainers can identify root, demo, package, or optional dependency failures per D-04 and D-21. |
| T-28-SC | Tampering | npm/pip/cargo installs | accept | No npm, pip, or cargo packages are installed by this plan; no new external packages are introduced. |
