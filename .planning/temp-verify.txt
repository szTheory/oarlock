## Phase Details

### Phase 8: Reliability Primitives

**Goal**: HTTP layer survives real-world Paddle production conditions — duplicate POST safety, transient failure recovery, and uniform error shape.
**Depends on**: v1.1 closed (Phase 7).
**Requirements**: REL-01, REL-02, REL-03
**Success Criteria** (what must be TRUE):

  1. Every create/start public function that truthfully supports idempotency semantics (Customers, Addresses, Transactions, and the corrected Phase 10 recurring-start path through `Paddle.Transactions.create/3`) accepts an `idempotency_key:` opt; an adapter-backed test asserts the value is forwarded as the `Idempotency-Key` HTTP header.
  2. An adapter-backed test exercises a 429 response with `Retry-After: 2` and the request succeeds after the client honors the retry; a sibling test asserts no retry on 4xx other than 429 and a max-3-retry ceiling on 5xx.
  3. A simulated transient network failure (timeout / nxdomain) returns `{:error, %Paddle.Error{network_error?: true, retryable?: true}}` with the existing `:raw_data` field still present (additive change only).
  4. The full pre-existing test suite (≥111 tests at v1.1 close) continues to pass with zero failures — no v1.1 seam regression.

**Plans**: 4 plans

  - [x] 08-01-PLAN.md — Atomic rename `:raw → :raw_data` in `%Paddle.Error{}` + add explicit `false` defaults for `:network_error?` and `:retryable?` (defexception keyword-syntax migration); co-update `guides/accrue-seam.md:118` and `CHANGELOG.md` in a single commit per D-02. (Wave 1, foundation for REL-03.)
  - [x] 08-02-PLAN.md — REL-03 transport-error normalization: add `Paddle.Error.from_transport/1` (with `transport_type/1` multiclause covering D-14 taxonomy `network_timeout|network_nxdomain|network_closed|network_unknown`); refactor `Http.request/4` `{:error, %Req.TransportError{}}` arm; four adapter-backed reason-variant tests in `http_test.exs`. (Wave 2, depends on 08-01.)
  - [x] 08-03-PLAN.md — REL-01 idempotency-key plumbing: `Keyword.pop(:idempotency_key)` + `ArgumentError` validation in `Http.request/4` (Pitfall 3 ordering); add trailing `opts \\ []` to `Customers.create/3`, `Customers.Addresses.create/4`, `Transactions.create/3`; six unit tests + one integration test locking the locked v1.2 opts vocabulary `:idempotency_key + :retry`. (Wave 3, depends on 08-01 + 08-02.)
  - [x] 08-04-PLAN.md — REL-02 retry policy: add `retry: :transient, max_retries: 3` to `Paddle.Client.new!/1`; five Agent-backed retry tests in `http_test.exs` covering 5xx-then-success, 4xx-no-retry, 429-then-success, per-call `retry: false` opt-out, and max-3 ceiling; CHANGELOG entry. (Wave 4, depends on 08-01..08-03.)

### Phase 9: Pagination Ergonomics

**Goal**: Consumers iterate any list endpoint without hand-rolling cursor loops, while the locked per-resource `list/2` shape stays untouched.
**Depends on**: Phase 8 (idempotency/retry harness reused for streaming requests).
**Requirements**: PAGE-01
**Success Criteria** (what must be TRUE):

  1. `Paddle.stream/3` (or per-resource equivalent) returns an `Enumerable` that, given a fixture of three cursor pages, yields every item from every page in order and terminates cleanly.
  2. `Paddle.all/3` returns the same items as `Paddle.stream/3 |> Enum.to_list/1` for the same fixture.
  3. A regression test re-asserts that `Paddle.Subscriptions.list/2` (and at least one other locked `list/2`) still returns `{:ok, %Paddle.Page{}}` — the v1.1 locked shape is unchanged.
  4. `Paddle.Page.next_cursor/1` remains the documented cursor accessor; auto-pagination is built on top of it, not as a replacement.

**Plans**: 1 plan

  - [x] 09-01-PLAN.md — Per-resource auto-pagination helpers for subscriptions and customer addresses, backed by hidden `Paddle.Internal.Pagination`, adapter-backed stream/all/list-shape/cursor replay tests, and public docs/changelog updates. (Wave 1.)

No public `Paddle.Subscriptions.create/2` is introduced.
  2. `Paddle.Subscriptions.pause/3` and `Paddle.Subscriptions.pause_immediately/3` return updated `%Paddle.Subscription{}` values with hydrated `:scheduled_change` / `:management_urls`, validated lifecycle opts, explicit `idempotency_key:` rejection, and retry-only request opts — adapter-backed.

# Phase 12: Documentation Pass - Context

**Gathered:** 2026-06-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Documentation pass across the public API surface of the `oarlock` SDK.

This phase ensures all public modules and functions are properly documented with `@moduledoc` and `@doc`, rewrites the `README.md`, and finalizes the `getting-started.md` and `telemetry.md` guides. It aims to provide excellent developer ergonomics (DX) by making the SDK steady, precise, and explicit, without trying to teach Paddle's complex billing rules inline.

</domain>

<decisions>
## Implementation Decisions

### Code Examples Depth
- **D-01:** Adopt a "Hybrid Explicit" approach for code examples.
- **D-02:** At the module level (`@moduledoc`), provide exactly one full, copy-pasteable pipeline showing `%Paddle.Client{}` setup, the API call, and a `case` block handling both `{:ok, struct}` and `{:error, error}`.
- **D-03:** At the function level (`@doc`), the `client` instantiation may be elided (assume `client` is bound), but the example **must always** show the `{:ok, _}` and `{:error, _}` pattern match. Never hide the return tuple in examples.

### External Linking Strategy
- **D-04:** Mechanics inline; domain rules external.
- **D-05:** Document exactly what the Elixir types/structs are inline (e.g., parameter requirements, struct shapes, pagination handling).
- **D-06:** Do not explain Paddle billing logic (proration, tax rules, etc.) inline.
- **D-07:** Every `@doc` must end with a `## Related Paddle docs` section containing a direct link to the canonical Paddle Billing API reference. We defer to the provider for domain truth.
- **D-08:** Include a `## Provider behavior` section in docs for non-obvious footguns.

### Error Documentation Depth
- **D-09:** Exhaustive local atoms; broad provider structs.
- **D-10:** Typespecs must exhaustively list the error union (e.g., `{:error, :invalid_id | Paddle.Error.t()}`).
- **D-11:** Every local validation atom (e.g., `:invalid_transaction_id`) generated by the SDK before the network request must be explicitly documented in the `@doc`.
- **D-12:** Do not enumerate Paddle's API error codes. Document that all network and provider-side errors are normalized into a single `%Paddle.Error{}` struct, which preserves the original Paddle `code` and `request_id` for debugging.

### Claude's Discretion
- The exact layout and formatting of the rewritten `README.md` and guides, provided they align with the Oarlock brand book and prioritize the getting started narrative (customer -> address -> transaction -> checkout -> webhook -> subscription).

</decisions>

### Code Examples Depth
- **D-01:** Adopt a "Hybrid Explicit" approach for code examples.
- **D-02:** At the module level (`@moduledoc`), provide exactly one full, copy-pasteable pipeline showing `%Paddle.Client{}` setup, the API call, and a `case` block handling both `{:ok, struct}` and `{:error, error}`.

- **D-04:** Mechanics inline; domain rules external.
- **D-05:** Document exactly what the Elixir types/structs are inline (e.g., parameter requirements, struct shapes, pagination handling).

### Error Documentation Depth
- **D-09:** Exhaustive local atoms; broad provider structs.

- **D-12:** Do not enumerate Paddle's API error codes. Document that all network and provider-side errors are normalized into a single `%Paddle.Error{}` struct, which preserves the original Paddle `code` and `request_id` for debugging.

# Phase 12: Documentation Pass - Research

**Researched:** 2026-06-04
**Domain:** Elixir documentation standards (ExDoc) and Paddle API DX
**Confidence:** HIGH

## Summary

This phase focuses entirely on developer experience (DX) and documentation. We are elevating `oarlock` from a functional library to a genuinely production-ready SDK that an external Elixir developer can integrate using only hexdocs.pm without reading source code.

The primary strategy is "Mechanics inline; domain rules external." We will lean heavily on standard ExDoc conventions (`@moduledoc` and `@doc`) across all unsealed modules in `lib/paddle/`. We will rewrite the README and finalize our Getting Started guide, alongside introducing a Telemetry guide. Code examples will enforce an explicit `{:ok, struct} | {:error, error}` pattern matching paradigm to prevent "happy-path only" assumptions.

**Primary recommendation:** Use `mix docs --warnings-as-errors` throughout implementation as a fast feedback loop to guarantee no broken links or syntax issues. Systematically visit each module, enforcing D-02 (pipeline examples on `@moduledoc`) and D-03 (pattern-match examples on `@doc`). 

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| API Documentation | API / Backend | — | The Elixir compiler and ExDoc extract metadata directly from the source AST. The SDK boundary is entirely Backend-owned. |
| Guides / Markdown | API / Backend | — | Long-form markdown (`README.md`, `guides/*.md`) bridges onboarding for SDK consumers. |

## Architecture Patterns

### Recommended Documentation Structure

```
lib/paddle/
├── [module].ex       # Starts with @moduledoc, followed by functions with @doc
guides/
├── getting-started.md # Narrative onboarding path
├── telemetry.md       # Operational metrics documentation
└── accrue-seam.md     # Locked consumer-facing contract
```

### Pattern 1: Module-Level Hybrid Explicit Pipeline
**What:** The `@moduledoc` block demonstrates the full, explicit lifecycle of a resource.
**When to use:** At the top of every public module.
**Example:**
```elixir
@moduledoc """
Provides operations for managing Paddle Customers.

## Example Pipeline

```elixir
client = Paddle.Client.new!(api_key: "...", environment: :sandbox)

case Paddle.Customers.create(client, email: "ada@example.com", name: "Ada Lovelace") do
  {:ok, %Paddle.Customer{} = customer} ->
    # Store customer.id
    IO.puts("Created: #{customer.id}")

  {:error, %Paddle.Error{} = error} ->
    # Handle API or network errors
    IO.puts("Failed: #{error.message}")
end
```
"""
```

### Pattern 2: Function-Level Explicit Pattern Match
**What:** The `@doc` block elides client instantiation but always handles the tagged tuple return.
**When to use:** On every public function.
**Example:**
```elixir
@doc """
Retrieves a customer by ID.

## Examples

```elixir
case Paddle.Customers.get(client, "ctm_123") do
  {:ok, %Paddle.Customer{} = customer} ->
    customer

  {:error, :invalid_customer_id} ->
    # Handle local validation error

  {:error, %Paddle.Error{} = error} ->
    # Handle provider/network error
end
```

## Provider behavior
If a customer is archived, they are still returned but `status` will be `"archived"`.

## Related Paddle docs
- [Get a customer](https://developer.paddle.com/api-reference/customers/get-customer)
"""
```

### Anti-Patterns to Avoid
- **Implicit returns:** `customer = Paddle.Customers.get!(client, "123")` (Avoid bang-functions in examples; oarlock enforces tagged tuples).
- **Eliding the error case:** Code blocks that only show `{:ok, struct} = ...` without demonstrating the error shape.
- **Billing domain tutorials:** Explaining how Paddle calculates taxes or prorations within the SDK docs instead of linking out.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Example Code Verification | Custom grep scripts for code blocks | ExDoc / ExUnit Doctests | Native Elixir tooling guarantees code examples compile and parse correctly. |
| Linking across modules | Markdown URLs | `[Module](`Module.html`)` or `m:Module` | ExDoc native autolinking prevents dead links on refactors. |

## Common Pitfalls

### Pitfall 1: Breaking `mix docs` with bad markdown
**What goes wrong:** Generating docs fails or has unformatted blocks.
**Why it happens:** Improperly indented markdown or missing language tags (e.g. ```elixir).
**How to avoid:** Run `mix docs --warnings-as-errors` locally continuously during the implementation phase.

### Pitfall 2: Over-documenting internal module signatures
**What goes wrong:** Private modules (`Paddle.Http`) start showing up in the generated docs, bloating the surface.
**Why it happens:** Changing `@moduledoc false` to `@moduledoc "..."`.
**How to avoid:** Respect the lock on the 5 original sealed modules (`Paddle`, `Paddle.Http`, `Paddle.Http.Telemetry`, `Paddle.Application`, `Paddle.Internal.Attrs`), plus `Paddle.Internal.Pagination`.

### Pitfall 3: Failing to document telemetry schemas
**What goes wrong:** A developer tries to attach to `[:paddle, :request, :start]` but has to read the source to know what metadata is provided.
**Why it happens:** Vague telemetry guides.
**How to avoid:** DOCS-05 strictly mandates publishing exact measurement and metadata schemas in `guides/telemetry.md`.
